# Development Guide

> Commands in this guide were executed during the audit where marked ✅. Results are recorded in `PROJECT_STATUS.md` §2 and below.

## 1. Prerequisites

- Node.js 20+ (audit machine: **v24.21.0**)
- pnpm 9+ (audit machine: **12.4.1**). The repo uses `pnpm-workspace.yaml` `allowBuilds` for `argon2`, `better-sqlite3`, `esbuild`.
- Native build toolchain for `argon2`/`better-sqlite3` (Python + make + a C++ compiler) if prebuilt binaries are unavailable.
- No external database server is required (SQLite is embedded).

## 2. Installation

```bash
pnpm install
```

`postinstall` runs `nuxt prepare`. ✅ Performed implicitly (dependencies present, build works).

## 3. Environment configuration

Create a `.env` file (git-ignored; there is currently **no** `.env.example` in the repo):

| Variable | Purpose | Default |
| --- | --- | --- |
| `NUXT_SESSION_SECRET` | Configured but currently **unused** by code | `development-secret-change-me` |
| `NUXT_DATABASE_PATH` | SQLite file path | `.data/simple-shop.sqlite` |
| `NUXT_APP_NAME` | Display app name | `Simple Shop Sales` |
| `NUXT_BOOTSTRAP_EMAIL` | First-user bootstrap email | empty (no user created) |
| `NUXT_BOOTSTRAP_PASSWORD` | First-user bootstrap password | empty (no user created) |

Do not commit real secrets. The bootstrap user is created only when the `users` table is empty **and** both bootstrap variables are set.

## 4. Database initialization and migrations

- The schema is applied automatically on server startup: `server/plugins/init.ts` runs `migrateDatabase()` (executes `server/database/migrations/001_init.sql`) followed by `seedPrimaryData()`.
- `seedPrimaryData()` ensures the `branch-main` branch and default ABAC policies exist, and creates the bootstrap admin when configured.
- The SQLite file and its `-wal`/`-shm` sidecars live in `.data/` (git-ignored); the directory is created automatically.

```bash
pnpm db:generate   # drizzle-kit generate (writes SQL under server/database/migrations/)
pnpm db:migrate    # currently a NO-OP: migrate.ts only default-exports migrateDatabase()
```

> ⚠️ Verified during audit: `pnpm db:migrate` exits 0 but creates an empty database file and applies no tables, because `server/database/migrate.ts` never calls its exported function. Schema creation happens only through the startup plugin. Also, `migrate.ts` hard-codes `001_init.sql`, so migrations generated by `db:generate` are **not** applied automatically. See `DATABASE.md` §5.

## 5. Development server

```bash
pnpm dev --host 0.0.0.0
```

✅ Verified: Nuxt 4.6.1 / Nitro 2.13.4 boots in ~4s. To isolate data while experimenting, set a throwaway path:

```bash
NUXT_DATABASE_PATH=/tmp/shop-dev.sqlite NUXT_BOOTSTRAP_EMAIL=admin@example.com \
  NUXT_BOOTSTRAP_PASSWORD='StrongPass123!' pnpm dev --host 127.0.0.1 --port 3123
```

## 6. First-user setup

1. Set `NUXT_BOOTSTRAP_EMAIL` and `NUXT_BOOTSTRAP_PASSWORD` before first start.
2. Start the server (schema + seed run on boot).
3. The bootstrap user is created with `clearanceLevel = 5`, `discountLimit = 30`, `branchId = branch-main`, so the seeded default policies permit all module actions.
4. Log in at `/login` (or the app root).
5. Afterwards the bootstrap variables can be removed; the user persists in the DB.

If no bootstrap variables are set and the `users` table is empty, no user is created and login is impossible until one is.

## 7. Tests and production build

```bash
pnpm test        # vitest --run     ✅ 4 files, 19 tests passed (isolated temp DB)
pnpm typecheck   # nuxt typecheck   ✅ exit 0
pnpm build       # nuxt build       ✅ exit 0, output in .output/
pnpm preview     # serve the production build (after build)
```

> ✅ Test isolation (roadmap T0.1) is implemented and verified. `tests/setup.ts` forces `NUXT_DATABASE_PATH` to a per-worker file under `<tmp>/simple-shop-sales-tests/` **before** the app DB module loads, so `tests/abac.spec.ts` deletes/reseeds policies in the throwaway DB only. `tests/global-setup.ts` removes the temp directory before and after the run. The developer DB `.data/simple-shop.sqlite` is never opened by the test process (confirmed with `strace`).

## 8. Manual smoke test (verified end-to-end)

With a fresh DB and bootstrap admin, the following flow was executed successfully during the audit:

1. `POST /api/auth/login` returns the user and a CSRF token; sets `shop_session` (httpOnly) and `shop_csrf` cookies.
2. `GET /api/me` returns the user attributes.
3. `POST /api/products` with `x-csrf-token` creates a product; `GET /api/products` lists it.
4. `POST /api/customers` creates a customer.
5. `POST /api/sales` creates a sale, decrements stock, and records the initial payment.
6. `POST /api/sales/:id/payments` records a follow-up payment (partial → balance updates).
7. `GET /api/sales/:id` returns receipt data incl. line items and payments.
8. `GET /api/reports/sales?from=…&to=…` returns correct totals.
9. Negative checks confirmed: mutation without `x-csrf-token` → **403**; unauthenticated `GET /api/me` → **401**; overpayment → **409**.

## 9. Production notes

- `pnpm build` produces `.output/`; run with `node .output/server/index.mjs`.
- Set `NODE_ENV=production` so session cookies receive the `Secure` flag (requires HTTPS).
- Set a strong `NUXT_SESSION_SECRET` if/when it is actually used (currently unused).

## 10. Backup and restore

SQLite, WAL mode:

- **Backup (safe while running):**
  ```bash
  sqlite3 .data/simple-shop.sqlite ".backup '.data/backup-$(date +%F).sqlite'"
  ```
  or stop the server and copy `.data/simple-shop.sqlite` together with its `-wal`/`-shm` sidecars.
- **Restore:** stop the server, copy the backup over `.data/simple-shop.sqlite`, and remove stale `-wal`/`-shm` files, or point `NUXT_DATABASE_PATH` at the restored file.
- A raw filesystem copy of only the `.sqlite` file while the server is running can miss WAL content — prefer the `.backup` command or offline copy.

## 11. Repository conventions

- Server routes: `server/api/<resource>.<method>.ts`, dynamic segments as `[id]`.
- Pure helpers live in `server/utils/` and are the preferred place for unit-tested logic.
- New documentation belongs in `docs/`.
